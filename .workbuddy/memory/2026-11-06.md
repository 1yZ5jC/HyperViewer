## Release 报 "Internal compiler error: 值对于 UInt32 太大或太小" 排查（未改代码）

- 结论：不是应用代码里的 uint 溢出。Release 启用 .NET Native（csproj 的 UseDotNetNativeToolchain=true），Debug 不启用，所以只有 Release 触发。
- 失败点：`obj\x86\Release\ilc\ilclog.csv`（x64 同）显示 ILC 1.7.27420.00 在 RunILTransforms / Mcg 阶段，打印「从 Windows Kits\10\lib\10.0.22621.0\um\...\WindowsApp.lib 读取 4906/4927 个导出」后抛 OverflowException（Convert.ToUInt32 溢出）。老编译器解析新版 SDK 导入库不兼容。
- 为何选中 1.7.6：`TargetPlatformMinVersion=10.0.10240.0` → `Microsoft.NETCore.UniversalWindowsPlatform 6.2.14` nuspec 的 `.NETCore5.0` 依赖组 → Microsoft.Net.Native.Compiler 1.7.6。本机同时装有 2.2.12（`UAP10.0.15138` 依赖组）及 2.2 框架包。
- 修复方向 A（推荐，可用于商店发布）：把 TargetPlatformMinVersion 提到 10.0.16299.0 并重新 Restore/Rebuild，切到 .NET Native 2.2.12；代价：最低系统版本升到 1709，发布包改依赖 .NET Native 2.2 框架包（AppPackages 里已有）。
- 修复方向 B（保 10240）：Release 各配置把 UseDotNetNativeToolchain 设为 false，仅出 IL 包用于本地侧载；商店会强制 .NET Native，不能用于正式发布；build-arm.ps1 依赖 native 产物会失效。
- 附带发现：csproj 第 91 行 `Debug|ARM64` 误设 `UseDotNetNativeToolchain=true`，与其他 Debug 配置不一致。
- 10:24 方案 C 已实测：**不可行**。注释掉 Default.rd.xml 的 `*Application*` 指令后 Release x86 仍在同一处崩溃（ilclog：Mcg 读完 WindowsApp.lib 的 4906 个导出后报错），仅 heap 从 169MB 降到 118MB，证明与反射指令/代码量无关。rd.xml 已恢复原样。
- 10:33 方案 A 已实测：**成功**。仅命令行 `/p:TargetPlatformMinVersion=10.0.16299.0`（未改 csproj）即触发 .NET Native 2.2.31116.00 ILC（ilclog 路径为 runtime.win10-x86.microsoft.net.native.compiler\2.2.12-rel-31116-00），BUILD_EXIT=0，完整生成本机代码并产出 `AppPackages\HyperViewer_0.0.22.0_Test\HyperViewer_0.0.22.0_x86.appxbundle`，AppxManifest 注入 Framework/Runtime 2.2 依赖。
- 结论纠正：工具链切换发生在 build 阶段按 `TargetPlatformMinVersion` 属性选择，**不依赖重新还原 NuGet**（本次 /t:Restore 后 project.assets.json 与 g.targets 仍是 1.7.6）；之前"必须重新 Restore"的说法过于保守。VS 里直接点 Release 仍会用 10240 → 1.7.6 → 崩溃，必须改 csproj 或带参数构建。
- 构建入口：PowerShell 工具直接调用 MSBuild.exe 会被安全策略拦截；改用项目 `build.ps1`（或临时脚本）+ `Set-ExecutionPolicy -Scope Process Bypass` 可正常构建；MSBuild 真实路径由 vswhere 得到为 `C:\Program Files\Microsoft Visual Studio\18\Enterprise\MSBuild\Current\Bin\MSBuild.exe`（不是 2022 路径）。
- 源码文件（csproj / Default.rd.xml / build-arm.ps1）均保持原样；obj/bin/AppPackages 里留有 2.2 成功产物；临时验证脚本已删除。构建另有 2 条 WMC1506 警告（MainPage.xaml 1308/1312 行 OneWay 绑定缺通知），与本次问题无关。

## 10:36 用户坚持 10240：找到并落地「不改最低版本」的方案（以下为最新状态，覆盖上文「未改源码」记录）

- 根因更精确：1.7.6 ILC 的 Mcg 读 `Windows Kits\10\lib\10.0.22621.0\um\<arch>\WindowsApp.lib` 的 4906(x86)/4927(x64) 个导出后 UInt32 溢出；10.0.26100.0 同类 lib 导出 4427(x64) 个（少 546 个 22621 独有导出），1.7 ILC 能正常解析。**不是时间戳**：把全部 0xFFFFFFFF 时间戳改成 0 的 22621 副本仍崩；导出名/序号/linker 偏移均无异常，具体触发项未定位。
- 修复（已写入 HyperViewer.csproj 末尾）：Release|x86/x64 条件属性 `IlcTargetPlatformSdkLibPath=$(WindowsSdkDir)Lib\10.0.26100.0\um`。必须放在 XAML targets 之后（`$(WindowsSdkDir)` 此时才定义）；放开头时 Exists 判断为假、属性为空。用 `msbuild -getProperty:IlcTargetPlatformSdkLibPath` 可快速验证。
- 该属性要指向 `...\um`（不含架构）：ILC 内部 `IlcInternals.targets:1974` 会拼 `\$(LibArch)`。指到 `...\um\x64` 会拼成双层导致找不到 lib（错误变为「未将对象引用设置到对象的实例」）。
- ILC 内置机制：目录里无 `WindowsApp.lib` 但有 `WindowsApp_downlevel.lib` 时自动改用 downlevel（`IlcInternals.targets:1982-1983`）；SDK 两个文件都有。
- 实测（普通构建、无任何命令行覆盖）：x64/x86 均 BUILD_EXIT=0，ilclog 无 Error，产出两个 appxbundle；AppxManifest 仍 `MinVersion=10.0.10240.0` / `MaxVersionTested=10.0.22621.0`，依赖 `Framework.1.7` + `Runtime.1.7`，`ilc.exe 1.7.27420.00`。
- 2.2 框架包自身 MinVersion=10.0.10049.0，但换 2.2 工具链会把应用清单 MinVersion 提到 16299，故不算「坚持 10240」。
- 限制：26100 SDK 无 arm(32) 导入库，条件排除 ARM；arm64 在 build-arm.ps1 中已用 2.2 工具链不受影响。换机器若未装 26100 SDK，Exists 条件使属性不生效（回退旧行为仍会崩）。
- 未改动：TargetPlatformMinVersion / TargetPlatformVersion / Default.rd.xml / build-arm.ps1 / NuGet 依赖；`Debug|ARM64` 误设 `UseDotNetNativeToolchain=true` 仍在（未动）。临时验证脚本与 lib 副本已清理。
